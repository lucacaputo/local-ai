## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Anything inside a sandbox can be read or run by the agent, and a web page or an email can try to steer it (doc-003 AN4, AN8). Docker Desktop exposes the host to containers as host.docker.internal, so by default a sandbox can reach the control service, llama-swap and devices on the LAN. If it held the router key it could also call Claude models, which the agent must never do (local only, and they cost money). decision-011 leaves the design open: an internal network plus an egress proxy, or firewall rules.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 From inside a sandbox the internet and the router are reachable, and llama-swap, the control service, other host ports and LAN addresses are not; tests show both
- [x] #2 A sandbox holds its own router credential, not the router key; with it the local models answer and Claude models are refused
- [x] #3 Revoking a sandbox credential stops that sandbox only, and no credential is written to the repo or logged in plain text
- [x] #4 The design and its tests are recorded in doc-004, with a decision record

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Network: each sandbox on its own internal Docker network sandbox-<user> (fixed subnet), with no route out: probed on Docker Desktop 4.98, a container there reaches neither host.docker.internal, the internet, nor the LAN (on the default bridge it reaches the router, llama-swap 8080, control 4100 and 192.168.1.1). Ports cannot be published from an internal network, so inbound goes through the gate too.
2. Gate: one container, local-ai-gate, on the default bridge and on every sandbox-<user> network, built from the pinned node alpine image with a small dependency-free Node program and node:test tests. (a) Forward proxy :3128 for HTTP and CONNECT: ports 80 and 443 only; resolves the name itself, refuses loopback, private, link-local, CGNAT/tailnet, multicast, ULA and Docker Desktop addresses, then connects to the checked IP (no DNS rebinding); one exception, the router (host.docker.internal:4000, /v1/ paths only). Logs destination host, port and verdict, never headers or bodies. (b) TCP forward 127.0.0.1:18789 on the PC -> sandbox-<user>:18789 for the Control UI; trustedProxies becomes the gate's fixed address on that network. Alternative considered: Squid + socat (proven parser, two images, no tests of ours); firewall rules in the Docker Desktop VM (not persistent, hard to test).
3. OpenClaw config: proxy.proxyUrl http://gate:3128 (managed forward proxy), web_fetch useTrustedEnvProxy, HTTP(S)_PROXY for the shell and Python, Chromium through the proxy; NO_PROXY and the browser bypass list only for *.test (bench fixture network). The provider keeps baseUrl host.docker.internal:4000, reached through the gate's router exception.
4. Credential: per-sandbox router key in Credential Manager (local-ai/sandbox-<user>-router), generated by sandbox.ps1 and passed to the container instead of the router key. config/custom_auth.py accepts it by SHA-256 hash from D:\local-ai\sandbox-keys.json (hashes only, reloaded when the file changes, outside the repo) and lets it call only the local models on /v1 chat/completions and models; anything else, Claude models included, gets 403. sandbox.ps1 revoke -User x removes that hash and key; other sandboxes and clients are untouched.
5. Tests: scripts\test-sandbox-net.ps1 (or bench-style Node) probes from inside the sandbox: internet 200, local model answers with the sandbox key; llama-swap, control service, other host ports, LAN, tailnet and the router with Claude models or the master key all refused; after revoke the sandbox gets 401 and the owner's clients still work. Bench: B3 or U2 still passes through the gate.
6. doc-004 section and a decision record (design, alternatives, test results); README sandbox section.
<!-- SECTION:PLAN:END -->

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
Each sandbox is on an internal Docker network of its own with no route out; its gate (sandbox/gate, TypeScript, no deps) is the only way in or out (decision-015). The gate is a forward proxy (ports 80/443, public addresses only, checked after its own DNS lookup and connected by the checked IP), a router pass on gate:4000 (/v1/ only, identity and forwarding headers dropped, requests stamped x-local-ai-sandbox), a TCP forward for the Control UI, and a placeholder-only DNS (198.18.0.1, nothing forwarded). OpenClaw, its browser (proxy flag, <-loopback>, private-network check off by owner decision), web_fetch, the shell and Python use the proxy. Each sandbox has its own router key (Credential Manager; the router knows only its SHA-256 in D:\local-ai\sandbox-keys.json, reloaded on change): models list and local-* chat only, 403 for Claude, Anthropic and admin routes; a stamped request is never let in by Tailscale identity or the master key. sandbox.ps1 revoke cuts one sandbox off at once. Fixed on the way: a sandbox could pass as the owner on the router by setting Tailscale-User-Login (open since TASK-041). Verified: scripts\test-sandbox.ps1 -Revoke, 26/26; gate unit tests 11/11, tsc clean; agent turns with web_fetch and the browser; bench B3 PASS through the gate; no key or token in any log. Follow-ups: one OpenClaw startup request to clawhub.ai goes out (owner: leave it); programs on the PC can still set the identity header on the router's loopback port (accepted in TASK-022).
